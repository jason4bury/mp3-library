# MP3 Library

A self-hosted, searchable database for your MP3 collection. It scans your music folder, reads ID3 tags (title, artist, album, year, genre, track number, duration), pulls embedded cover art straight out of the MP3 files, and matches artist photos from a separate folder on disk. Everything is served through a small web app with search/filter, an artist browser, playlists, a built-in player, and a library health page.

## How it works

- **Scanning**: on first start (and whenever you click "Rescan"), the app walks `MUSIC_DIR` recursively for `.mp3` files, reads their tags with [music-metadata](https://github.com/Borewit/music-metadata), and stores everything in a SQLite database in `DATA_DIR`. Rescans are incremental — only new or changed files (by modified time) are re-read. `MUSIC_DIR` can be a single folder or a comma-separated list (`/music/collection1,/music/collection2`) if your MP3s are split across more than one folder. If you're running via Docker, don't edit this directly — it's a container-internal path; set `MUSIC_HOST_DIR_1`/`MUSIC_HOST_DIR_2` in `.env` to your real folders instead (see "Running it" below). While a scan is running you'll see it: the Rescan button disables itself and says "Scanning…", a thin progress bar appears under the top bar, and the status text next to it counts up with a live "X/Y (Z%)" — first counting the whole library (fast — it's just listing folders), then working through it for real. If a scan hits an unexpected error it says so right there ("Scan failed: …") instead of just going quiet. When a scan you kicked off with **Rescan** finishes, a popup summarizes exactly what changed — files added, updated, and removed, plus a count of any that errored out (or "No changes" if nothing did) — so you don't have to squint at the small status text to know it worked. That popup only shows up for a scan you actually triggered and watched; the automatic scan on first start, and just having the page open while a scan happens to finish, don't pop anything up.
- **Cover art**: embedded pictures are extracted once per album (deduplicated by artist+album, since most tracks on an album share the same embedded image) and stored in the database, then served at `/api/cover/track/:id`.
- **Artist photos**: matched by folder name to each artist in `ARTIST_PICTURES_DIR`. Your layout — `Artist Pictures/<Artist Name>/folder.jpg` — is exactly what it expects: it looks for `folder.jpg` (or `folder.png`/`.jpeg`/`.webp`, falling back to any image) inside the subfolder whose name matches the artist. Matching ignores case, accents, a leading "The", and punctuation, so "The Beatles" and "beatles" both match a `Beatles/` folder. If photos aren't showing up, the Health tab's "Artists without photo" tile is clickable — it shows the resolved folder path, whether it could even be read, exactly which folder names it found on disk, and which artists it couldn't match, so you don't need shell access to figure out whether it's a mount problem or a naming mismatch.

  Photos are **imported into the database** (same idea as embedded album cover art) rather than read from `ARTIST_PICTURES_DIR` on every request — every page that shows a photo (Artists, an artist's own page, Albums, Health, the login background) is a plain DB lookup, not a live filesystem read. The import runs once at server startup and again at the end of every rescan; a restart with nothing changed on disk skips straight past (it only re-reads a photo whose file has actually changed since it was last imported). A newly added or changed artist photo shows up after the next restart or Rescan, not instantly — that's the trade-off for not touching the filesystem on every page view, which matters a lot if `ARTIST_PICTURES_DIR` is a network share.
- **Login background**: the sign-in page shows a tiled, rotated mosaic behind the card (similar to Jellyfin's login screen), mixing both artist pictures from `ARTIST_PICTURES_DIR` and embedded album cover art — so it looks varied even on a library with only a handful of curated artist photos, or none at all. The specific picture set is deliberately **static between rescans** — it's picked once when a library rescan finishes (manual or the automatic first-run scan) and stays that way until the next one, rather than reshuffling on every page load. The mosaic is a dense grid (140 small tiles) rather than a few large ones, so a modest picture set still tiles the whole screen without looking repetitive up close. It's rendered directly into the login page's HTML on the server, not built by client-side JavaScript after the page loads, so it's there from the very first paint instead of popping in a moment later. With nothing scanned/matched yet, the login page just falls back to its plain dark background — nothing broken, nothing to configure.
- **Search**: full-text search (title/artist/album/genre) plus dropdown filters for artist, album, year, and genre, combinable and paginated. The topbar search box also shows live suggestions as you type — top matching artists, albums, and tracks — so you can jump straight to an artist/album page, or filter the Tracks tab down to one track, without waiting for the full results to load first. Clicking a suggestion never starts playback, same rule as everywhere else in the app.
- **Playback**: click the ▶ button next to a track to stream it through the built-in player (range requests supported, so seeking works) — clicking elsewhere on a track row/line is safe and won't start playback, so you can browse, select checkboxes, or click an artist/album link without accidentally interrupting what's already playing. On the Tracks tab, the artist and album names are separate links — click an artist to open their Artist Info, or an album to open its own Album detail page. The 🔀 button in the player bar toggles shuffle — with it on, whatever queue you're playing through (the Tracks tab's current filtered list, an album, a playlist) advances in a randomized order instead of top-to-bottom, without changing which tracks are actually in it. The **Shuffle All** button on the Tracks tab is a shortcut to the same thing for your whole library at once — it ignores whatever filters are currently applied and just starts a randomized queue of everything, no playlist or filtering required. Next to it, **🌱 Rediscover** is a different kind of shuffle: instead of even odds across everything, it biases toward tracks you've never played or haven't played in a long time, so it's a good way to surface stuff that's gotten buried. The player bar also has a volume slider and mute button (🔊/🔉/🔇) — your level is remembered in the browser between visits. The app also remembers **what you were last playing and roughly where** — reopen it later (a fresh page load, or logging back in after signing out; it's saved in the browser, independent of your login session) and the player bar shows that track paused at its last position, ready to pick up with one press of ▶ (it deliberately doesn't auto-play on load, since browser autoplay is unreliable and unsolicited audio on page load is bad manners anyway). It's not just the one track, either — whatever queue it was part of comes back too (the Tracks tab's list, an album, Shuffle All, Radio, a playlist, …), so the Now Playing panel and "what plays next" are exactly as you left them; a saved playlist is re-fetched fresh rather than replayed from a snapshot, so it also picks up anything you'd edited into it since.
- **Keyboard shortcuts**: with focus somewhere other than a text field or dropdown, Space toggles play/pause, ← and → seek 5 seconds back/forward, and ↑ and ↓ turn the volume up/down. They're ignored while you're typing into search, a filter, or a dialog, so they never steal a keystroke from something you're actually typing.
- **Radio** *(📻 button next to any track — Tracks tab, an artist's Albums & Tracks list, or an Album detail page)*: starts an ad-hoc queue built around that one track, mixing in similar artists (via Last.fm, reusing whatever's already cached from viewing Artist Info — no extra API calls) with a same-genre/same-artist fallback so it still works fine with no `LASTFM_API_KEY` set. It's just another queue — the ▶ buttons everywhere still start playback the normal way, and Radio never runs on its own without you clicking 📻.
- **Gapless crossfade** *(optional, off by default — turn it on in ⚙ Settings)*: fades the outgoing track out while fading the next one in, instead of a hard cut, over a duration you choose (1–12s). Off by default because a hard cut is the more predictable choice for most listening; when it's on it applies to every automatic track change (shuffle included), not just an explicit Radio/playlist queue.
- **Artist detail**: opening an artist has two sub-tabs — **Artist Info**, a bio/tags/similar-artists panel from Last.fm plus a list of their albums (with a small cover thumbnail — hover it to see the full cover art in a popup, and click that popup to jump straight to the album), and **Albums & Tracks**, the full per-album track listing with playback and "add to playlist". Opening an artist always starts on Artist Info. Hovering the big artist photo at the top also pops up a closer look at it.
- **Album detail**: a dedicated **Albums** tab lists every album in your library (cover, artist, year) — click one for its own page with the full cover, track listing, playback, and "add to playlist"; the artist's name there links back to their Artist Info. Album names are clickable from anywhere they appear (the Tracks tab, the Artist Info album list) and always land here. Hovering the big cover on an album's own page pops up a closer look at it.
- **Picture previews**: on the Artists and Albums tabs (the grids you browse), hovering a photo or cover pops up a bigger version near the cursor — click that popup to jump straight to that artist's or album's page, same as clicking the card itself. The popup stays open if you move your mouse onto it (so there's time to actually click it), and closes once you move away from both it and the picture that triggered it.
- **Last.fm enrichment** *(optional)*: if you set `LASTFM_API_KEY`, the Artist Info tab shows a short bio, genre tags, similar artists, and listener/play counts pulled from Last.fm, with a link back to the artist's Last.fm page — and the Album detail page shows the same kind of thing for that album (summary, tags, listener/play counts, a link to its Last.fm page). Results are cached in SQLite (30 days for a normal hit, 1 day for "not found", 1 hour for a Last.fm outage) so it's not re-fetching on every page view — there's a "Refresh" link if you want to force an update. Without a key, these sections just explain how to get one (it's free) and everything else in the app works exactly the same.
- **Scrobble to Last.fm** *(optional, needs `LASTFM_API_KEY` + `LASTFM_API_SECRET`)*: connect your Last.fm account from ⚙ Settings — it opens Last.fm's own authorization page in a new tab, and there's a button to click once you've approved it there. Once connected, every track you play updates your Last.fm "now playing" status immediately, and gets scrobbled once it's been playing for half its length or 4 minutes (whichever is lower) — Last.fm's own eligibility rule, so a track you skip early never gets scrobbled. Disconnect any time from the same Settings panel.
- **Playlists**: create playlists from the Playlists tab or the "+" button next to any track (in the Tracks list or an artist's album view). Reorder by dragging a track (grab the ⠿ handle) or with the up/down arrows, remove tracks, rename or delete a playlist, hit "Play all" to queue the whole thing, or export it as a standard `.m3u8` file (handy for pulling it into another player or playlist tool — note the exported paths are the same absolute paths the container sees, so they're only directly usable somewhere that mounts your library the same way). You can also **import** an existing `.m3u`/`.m3u8` playlist via the "Import playlist" button — it matches each line to a track in your library (exact path first, then by filename alone, since an imported playlist's paths rarely match this container's mount paths byte-for-byte) and tells you how many tracks matched, were ambiguous (several tracks share a filename), or weren't found. On the Tracks tab, check the box next to any tracks to select several at once and add them all to a playlist in one go with the "Add to playlist" bar that appears.
- **Now Playing panel**: a box on the right that's always on screen, showing the queue behind whatever's currently playing — not just saved playlists, but the Tracks tab's current list, an artist's or album's tracks, Shuffle All, Rediscover, Radio, History, or a recap "On this day" group — with whichever track is playing highlighted, following along as playback advances, and each track has its own ▶ to jump straight to it. Before you've played anything it just shows a "Nothing playing yet" placeholder rather than being hidden. It doesn't fully close — the **–** button minimizes it down to just its title bar (out of the way, but still there), and **▢** brings it back; whichever you left it as is remembered between visits. Playing a real playlist ("Play all", or a track inside one) automatically maximizes it if it was minimized, same as it's always popped open; every other queue type just updates its contents without changing whether it's minimized.
- **Queue management**: every track row (Tracks tab, an artist's Albums & Tracks list, an Album detail page) has two extra buttons — **⏭ Play next** and **📃 Add to queue** — for building up what plays after the current track without leaving what you're browsing. A track already sitting somewhere else in the queue is *moved*, not duplicated, so using either button on a track you already queued just repositions it. In the Now Playing panel itself, each track (other than the one currently playing) has a **✕** to remove it from the queue, and you can drag tracks by their ⠿ handle to reorder the upcoming queue by hand — same drag-and-drop as reordering a playlist. Doing any of this to a plain playlist's queue quietly turns it into an ad-hoc "Now Playing" queue (so your saved playlist itself is never edited by accident); reordering is only available while shuffle is off, since there's no fixed order to drag while it's on.
- **Smart (auto-updating) playlists**: set up a search on the Tracks tab — any mix of the text search, artist/album/year/genre filters, and the Favorites toggle — then click "Save as smart playlist". Unlike a regular playlist, it doesn't store a fixed list of tracks: every time you open it, it re-runs that saved search against your current library, so newly-scanned or newly-tagged tracks that match show up automatically. Smart playlists are marked with a "Smart" badge, can be renamed/deleted/exported/played like any other playlist, but can't be manually reordered or edited (there's nothing fixed to reorder) — change the playlist's contents by adjusting what it searches for on the Tracks tab and saving a new one.
- **Generate a smart playlist by Artist/Genre/Year/Decade**: the Playlists tab has a "Generate smart playlist" toolbar with four buttons, in this order — **Artist**, **Genre**, **Year**, **Decade**. Each one pops up a dropdown of the actual values in your library for that dimension (e.g. Decade only lists decades you actually have tracks from) — pick one, then choose how many tracks: **all matching tracks** (the normal smart playlist behavior — every track that matches, same stable order every time), or a random count (10/20/50/100). Picking a random count creates the playlist with that many tracks chosen at random from the matching set, and — since a smart playlist's contents are always recomputed live — it's a *different* random pick every time you open it, not a fixed subset saved once. The playlist is named after the value you picked (e.g. "1990s", or "1990s (20 random)" for the randomized version), and both kinds can coexist side by side. If a playlist with that exact name already exists, it tells you rather than making a duplicate.
- **Generate ALL playlists at once, as fixed playlists**: below that is a second toolbar, "Generate all as fixed playlists" — same four buttons (Artist/Genre/Year/Decade), but each one bulk-creates one playlist per *every* distinct value for that dimension in one go (e.g. Decade makes a "1960s (fixed)", "1970s (fixed)", "1990s (fixed)"… for every decade you actually have), shows a count and asks for confirmation first, and skips anything that already exists by that exact name. Unlike the smart playlists above, these are regular playlists — the matching tracks are captured once, at creation time, so they won't change afterward even if your library does (add/remove/retag tracks all you want); you can reorder or remove tracks from them by hand just like any other regular playlist. They're named with a "(fixed)" suffix so a "1990s" smart playlist and a "1990s (fixed)" fixed one can both exist side by side without colliding.
- **Favorites & play counts**: click the ♡ next to any track to favorite it (it turns into ♥) — on the Tracks tab, an artist's Albums & Tracks list, or an Album detail page, they all stay in sync with each other. The "Favorites" button next to the Tracks tab filters shows only your favorited tracks, and it's one of the criteria a smart playlist can be built from. Every track also tracks how many times you've played it from the start (seeking around within a track you're already playing doesn't count as a new play), when it was last played, and when it was first added to your library: the Tracks tab has sortable "Plays", "Last played", and "Added" columns (click any header — a "most played", "recently played", or "recently added" view is just a matter of sorting by one of them), and the album/artist track lists show a compact "N×" play count next to each track (hover it for the exact count and last-played time). "Added" only works going forward from when this feature was added — existing tracks scanned before then show "—" since there's no way to know when they were really added, rather than guessing.
- **Play history**: the History tab is a real, chronological log of individual plays — most recent first, paginated — separate from the "Last played" column (which only ever shows the single most-recent play per track). Each row has its own ▶ button to play it again; nothing in the list plays on click.
- **Listening recap**: above that full play log, the History tab shows a summary — total plays and top tracks/artists over the last 7 days, plus an "On this day" section surfacing anything you played on this same calendar day in a previous year (grouped by year, most recent first). It's computed entirely from your play history, so "on this day" only has anything to show once you've got history going back that far.
- **Health check endpoint**: `GET /healthz` is a plain, unauthenticated endpoint (no login cookie needed) that confirms the process is up and the database is actually readable — meant for uptime monitors (Uptime Kuma and similar), a reverse proxy's own health probe, or Docker itself. The Dockerfile wires it into a container `HEALTHCHECK`, so `docker ps` and tools like Portainer show a real Healthy/Unhealthy status instead of just "running". It's intentionally minimal (up/down plus scan status) — the in-app Health tab covers actual library diagnostics.
- **Backups**: the "⬇ Backup" button in the top bar downloads a snapshot of the library database (tracks, playlists, favorites/play counts/history, cached Last.fm data — everything except the actual MP3 files and cover art extracted from them) as a single `.db` file, taken safely even while the app is being used. Worth doing before a big library change, or just on a schedule; keep the file somewhere other than the same disk as your media.
- **Library health**: the Health tab shows counts of tracks missing a title/artist/album/year/genre tag, tracks with no cover art, artists with no matched photo, any files that failed to scan (bad/corrupt MP3s, unreadable folders), and possible duplicate tracks — click a tile to see the actual file list. Scan errors are tracked per-run in a `scan_errors` table, cleared and repopulated on each scan. "Possible duplicates" groups tracks that share the same artist and title (case-insensitive) and shows each group's copies side by side (album, year, genre, length, size, file path) so you can compare before deleting anything — it's a simple exact-match heuristic, so a live version or remaster with the same title can get flagged too; it's a starting point for cleanup, not a verdict.
- **Stats**: the Stats tab is a deep-dive on your whole collection. Tiles cover totals (tracks/artists/albums, total playtime, library size on disk, average bitrate), listening habits from your play counts and favorites (total time listened, how many favorites and what share of the library that is, how many tracks have never been played and their share, average track length, average tracks per album), and a couple of file-size highlights (largest and smallest track on disk). Below that are ranked breakdowns: by decade and by individual year; top genres both by track count and by disk space; top artists by track count, by album count, and by disk space; top albums by track count; most played tracks; and favorites broken down by genre. Anywhere a row names a genre, artist, year, or album, clicking it jumps straight to a filtered Tracks view (or that artist's/album's page) — except "Most played tracks", which is just a ranking to look at, consistent with nothing in this app starting playback on a click.

## Running it

1. Copy `.env.example` to `.env` and fill in real values. **You only need to edit `.env`** — `docker-compose.yml` reads everything (including your music folder paths) from it, so there's no need to open that file too. At minimum, set:
   - `MUSIC_HOST_DIR_1` (and `MUSIC_HOST_DIR_2` if you have a second folder) to your real music folder(s) on this machine — e.g. `d:/music` on Windows, `/home/you/Music` on Linux.
   - `ARTIST_PICTURES_HOST_DIR` to your real Artist Pictures folder.
   - `APP_USERNAME`/`APP_PASSWORD` and a random `SESSION_SECRET` (the file tells you how to generate one).
   - `LASTFM_API_KEY` is optional — grab a free one from [last.fm/api/account/create](https://www.last.fm/api/account/create) if you want artist bios/tags on the Artist Info tab and the Radio feature's similar-artist mixing, or leave it blank to skip that. Also set `LASTFM_API_SECRET` (from the same account page) if you want scrobbling — connect your account afterward from ⚙ Settings in the app.

   Only have one music folder? Delete the `MUSIC_HOST_DIR_2` line in `.env`, drop `,/music/collection2` from `MUSIC_DIR` in `.env`, and delete the matching `MUSIC_HOST_DIR_2` volume line in `docker-compose.yml` — that's the one case that still needs a one-line edit there.
2. From this folder, run:
   ```
   docker compose up -d --build
   ```
   If a required `.env` value is missing, Docker Compose will refuse to start and tell you exactly which one — it won't silently start with an empty/wrong music folder.
3. Visit `http://<your-server>:3000`, sign in, and the first scan will kick off automatically (watch the "Scanning… x/y" indicator in the top bar). Click **Rescan** any time you add new files.

The database lives at `${CONFIGS}/mp3-library` on the host (`CONFIGS` should already be set in your environment, alongside your other self-hosted services), so it survives container rebuilds. Your music and pictures folders are mounted read-only — the app never writes to them.

**If a scan finds 0 files:** the scan status indicator and the Health tab both show `files_found` — if that's 0, the app can't see anything under the paths you gave it. Confirm the mount actually worked with:
```
docker compose exec mp3-library ls -la /music/collection1
```
If that lists your MP3s, the mount is fine and the issue is elsewhere (check for a typo'd file extension, or a permissions issue in `docker compose logs mp3-library`). If it's empty or errors, double-check `MUSIC_HOST_DIR_1`/`MUSIC_HOST_DIR_2` in `.env` point at the right folder on the host, and — on Windows with Docker Desktop — that drive is shared with Docker (Settings → Resources → File sharing, if you're on the older Hyper-V backend; WSL2 backend shares all drives automatically).

## Since you're putting this on the internet

The app has its own login (single username/password, session cookie) so it's not wide open, but it's a simple hobby-app login — no brute-force lockout, no 2FA. Sessions are stored in the same SQLite database as everything else (see `sqliteSessionStore.js`), not in memory — so restarting/redeploying the container doesn't silently log you out, and it's why you won't see express-session's "MemoryStore is not designed for a production environment" warning in the logs. A few things worth doing given it'll be internet-facing, not just LAN:

- **Put it behind a reverse proxy with HTTPS** (Nginx Proxy Manager, Synology's reverse proxy, Caddy, Traefik — whatever you already use for your other Docker services). Don't forward port 3000 straight from your router. `app.set('trust proxy', 1)` is already set so session cookies behave correctly behind a proxy.
- **Change `APP_PASSWORD` and `SESSION_SECRET`** from the placeholder values before you expose it — the compose file will actually refuse to start if you leave them unset.
- Consider adding a layer in front of login itself (e.g. your reverse proxy's own basic-auth, or a rate limiter/fail2ban rule on repeated failed logins) since this app doesn't rate-limit login attempts on its own.
- If you don't strictly need public access, a WireGuard/Tailscale tunnel gets you "access from anywhere" without exposing the port publicly at all — worth weighing against a public URL.

## Project layout

```
server/
  index.js          # express app, sessions, static file gating
  auth.js           # login/logout/me
  sqliteSessionStore.js # express-session Store backed by the sessions table, instead of the default in-memory store
  db.js             # SQLite schema (tracks, album_covers, scan_status, scan_errors, playlists, playlist_tracks, play_history, lastfm_cache, lastfm_album_cache, lastfm_auth, login_background, artist_photos, sessions) + migrations
  scanner.js         # walks MUSIC_DIR, reads tags via music-metadata, upserts DB, records scan_errors
  artistPhotos.js    # matches artist names to folders under ARTIST_PICTURES_DIR, imports photos into the DB (startup + every rescan)
  loginBackground.js # picks/persists the login page's random artist-photo + album-cover mosaic pool, refreshed only on rescan (see scanner.js)
  loginPage.js       # server-renders login.html with that pool's tiles already inlined, so the mosaic shows up on first paint
  lastfm.js          # Last.fm artist.getinfo/album.getinfo client + SQLite-backed cache, plus scrobbling (auth, now-playing, scrobble)
  search.js          # FTS5 query builder
  routes/api.js      # all /api/* endpoints — tracks, artists, albums, playlists, health, streaming
public/
  index.html, css/, js/app.js   # vanilla-JS single-page frontend
  login.html                     # standalone login page
Dockerfile
docker-compose.yml
.env.example
```

Upgrading from an earlier version of this app: just drop in the new `server/` and `public/` folders and restart — `db.js` runs a small migration on startup (new columns/tables as needed) that's safe to run against your existing `library.db`. Nothing needs to be deleted or rescanned.

## Extending it later

Some natural next steps if you want them:
- Other formats (FLAC/M4A/OGG) — `music-metadata` already supports them; the scanner just needs its file filter widened past `.mp3`.
